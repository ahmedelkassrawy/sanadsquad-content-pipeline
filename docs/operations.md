## Running

The brief's example commands, exactly as written there:

```
python run_week.py --plan plan.json --output output/week-42
python run_week.py --plan plan.json --set thread_2="oracle manipulation"
python run_piece.py --type tech-thread --topic "reentrancy"
```

`--plan plan.json` falls back to `inputs/plan.json` when there is no `plan.json` in the
current folder. Run from the repo root, with the venv Python:

```powershell
& .\.venv\Scripts\python.exe run_week.py --plan plan.json --output output/week-42
& .\.venv\Scripts\python.exe run_week.py --plan plan.json --set thread_2="oracle manipulation"
& .\.venv\Scripts\python.exe run_piece.py --type tech-thread --topic "reentrancy"
```

With one `OPENROUTER_API_KEY` only, add
`--model-override openrouter:openai/gpt-4.1-mini`.

On macOS/Linux use `.venv/bin/python` instead of `.\.venv\Scripts\python.exe`.

Useful facts:

- Without `--output`, the run folder is `output/<UTC time>-<random>`. An existing folder is
  never overwritten.
- `--set slot_id=topic` sets a topic only. It is not evidence. The topic still has to be
  backed by a knowledge base entry or a fetched web page, or the slot fails.
- `run_piece.py` runs one slot (`piece_1`) through the same graph.
- The summary JSON goes to stdout. The start-up estimate line goes to stderr. On an error the
  command prints only `pipeline_error:<ErrorName>` and exits with code 2.
- Slot ids must be safe file names and unique ignoring case.

Flags for both commands: `--root`, `--output`, `--resume`, `--estimate`, `--no-advisor`,
`--default-model`, `--model-override`, `--reasoning-effort-override`, `--max-tweet-chars`,
`--max-concurrency`, `--token-budget`, `--cost-budget`, `--allow-unpriced`.
`run_week.py` adds `--plan` and `--set`; `run_piece.py` adds `--type` and `--topic`.
Run `run_week.py --help` for the list.

## Look at a run folder

Each run folder has a generated `README.md` that lists the files it contains. Start with
`posts.csv`, then `run.log` (what happened to each slot, step by step) and `run_summary.json`. Every record in the JSON files carries a
`slot_id` and an `attempt` number. JSON schemas are in [schemas/](../schemas/); they are
generated by `python -m content_pipeline.schemas --output schemas`.

| File | What it holds |
| --- | --- |
| `posts.csv` | The export: `Post Text, Image`, one row per shipped piece, in plan order. A thread is one cell with one tweet per line. Image paths are relative to the run folder. |
| `posts.json` | The same pieces with each tweet as a separate list item. |
| `plan.resolved.json` | The plan after `--set` and topic choice, with warnings (including `topic_proposal_rejected:<slot>:<id>` when the model's topic was refused) and `topic_reasons`, the model's one-line reason for each pick that code accepted. |
| `research_log.json` | Every source found for every slot, with its evidence text and status. |
| `drafts.json` | Each draft as the writer wrote it, the version after safe fixes, the fixes applied and any rule violations. |
| `review_report.json` | Scores per criterion, reasons, and the accept or reject decision. |
| `visuals.json`, `images/` | The image spec and the PNG card (or spec JSON) for each shipped piece. Each record names the backend (`cloudflare_flux`, `pillow_card`, or `spec_json` when no PNG could be drawn) and, when a fallback happened, a `fallback_reason` and a short `fallback_detail` list of codes. |
| `final.json` | The approved text and image of each shipped piece. |
| `run_summary.json` | One outcome per slot (`shipped`, `dropped_quality`, `failed_research`, `failed_api`, `failed_budget`, `failed_output`), tokens and cost in total and per agent (`agents`: research, writer, reviewer, visual, advisor; calls, tokens, USD, and the uncertain part; summed from `usage.jsonl`, so they can differ from the run totals, which come from the ledger, after a crash/resume or an unpriced response; absent in older runs), advisor status. |
| `usage.jsonl`, `ledger.json`, `external-usage.json` | One line per model call, the budget ledger, and search and image counters. |
| `advisor.json`, `advice.md`, `advice.patch` | Suggested instruction changes. Never applied for you. |
| `run.log` | Per-slot trail rebuilt from the JSON files: research, drafts, review scores and reasons, outcome, totals. |
| `README.md` | Index of the files this run folder contains. |
| `snapshot/` | A copy of the inputs and instruction files used by this run. |
| `checkpoint.sqlite`, `state.json`, `run_identity.json`, `runtime-settings.json` | Resume state. A live run has them. The committed sample leaves them out, so it cannot resume. |

A run with zero shipped pieces still writes a header-only `posts.csv` and a summary.

## Resume

```powershell
& .\.venv\Scripts\python.exe run_week.py --resume output/week-42
& .\.venv\Scripts\python.exe run_week.py --resume output/week-42 --token-budget 400000 --cost-budget 1.50
```

Resume continues from the saved checkpoint and the saved copy of the inputs. Edits to
the live files are ignored. The only settings you can change are `--token-budget` and
`--cost-budget`, and only upward. A finished run re-checks its saved stage files and returns its saved summary; if a saved
stage no longer matches its inputs, resume stops with `saved stage input mismatch` before
any model call. Two processes cannot use one
run folder at once. Billing is not exactly once: if a process dies after a call was billed
but before its result was saved, resume can pay for that call again. The batch topic choice is
not saved either: a resume after a crash inside the topic node asks the model again, and if the
answer changed, a slot whose research was already saved fails (`failed_research`) rather than
swap topics (see [Topic selection](../ARCHITECTURE.md#topic-selection-decision-and-alternatives)).
Topic history is read from every sibling folder of the run folder, so use an empty parent folder
for a clean history.

## Advisor

After export, an advisor agent reads the run's evidence and suggests edits to the brand
voice, the writer instructions and the rubric. Code builds `advice.patch` from its edits,
refuses edits to machine rules or to lines with numbers, and never applies anything.
Read the patch yourself before using it. The advisor is optional and outside the brief. It is off by default (`ADVISOR_ENABLED=false`); set
`ADVISOR_ENABLED=true` to turn it on. A small model such as `ministral-14b` often fails here: it
must copy file hashes and exact unique text from about 20,000 tokens of input, and any slip is
refused and recorded as `failed_output`. If it fails, the failure is recorded and the posts still ship.

## The config/ folder

Four small files, each loaded by a specific part of the code:

- `config/repair.md`: the prompt sent back to a model when its structured output fails to
  parse or validate, asking it to re-emit valid output. Loaded by `content_pipeline/model_client.py`.
- `config/visual.yaml`: the ordered list of image backends (for example Cloudflare FLUX, then
  the Pillow card fallback). The first backend that works is used. Loaded by
  `content_pipeline/config.py`.
- `config/prices.yaml`: USD per million tokens for models `genai-prices` does not know (for
  example Mistral `ministral-14b-latest`), checked first. Loaded by `content_pipeline/model_client.py`.
- `config/live-review-controls.json`: one known-supported and one known-unsupported draft.
  `content_pipeline/live_proof.py` sends them to the live reviewer to prove it rejects invented
  claims and accepts grounded ones. The file also has an `unsupported_general_text` entry that
  no code currently reads.

`repair.md` and `visual.yaml` are copied into every run folder snapshot, and so is `prices.yaml`
(resume uses the saved copy; runs saved before this change have none and use no overrides).

## Scripts

- `scripts/run_offline_demo_with_fake_models.py --output <new-folder>`: runs the whole
  pipeline with scripted fake models: no model or search calls. Cloudflare images are still made
  if the two Cloudflare keys are set, else a Pillow card. Verification only.
- `scripts/export_run_as_sample_output.py --source <run-folder> --output <new-folder>`: copies a
  finished run into the publishable sample output folder, leaving out checkpoints, locks and
  credentials.

## Checks you can run offline

These make no model or search calls. Python is the venv Python.

```powershell
& .\.venv\Scripts\python.exe -m pytest -q
& .\.venv\Scripts\python.exe -m pip check
& .\.venv\Scripts\python.exe -m content_pipeline.schemas --output <new-folder>
& .\.venv\Scripts\python.exe -m content_pipeline.live_proof
```

`live_proof` without `--live` only prints `NOT_RUN`. With `--live` it calls real models
(reviewer control and a full sample); see its `--help`. Tests use scripted models, so they
prove routing and rules, not the quality of a real model's judgement.
